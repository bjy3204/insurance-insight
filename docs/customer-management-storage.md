# 고객관리 저장 설정

고객관리 데이터는 스프레드시트 연결과 별개다. 기존 `customer_settings.customer_url`은 수정하지 않는다.

## 적용

현재까지의 통합 실행 파일: `outputs/supabase/insurance-insight-20261015-all.sql`. 고객·계약, 유입경로 목록, 드래그 순서 RPC, 캘린더 기본 테이블·확인 체크·구분·알림, 기존 시트 연결 저장소와 메뉴 순서를 한 트랜잭션으로 묶었다. 기존 프로젝트의 `profiles`, `customer_settings`, `auth.users`를 전제로 한다. 기존 테이블은 유지하며, 실제 DB에서 이 통합 파일의 실행 성공 여부는 아직 확인하지 않았다. SQL Editor에서 실행할 때는 이 통합 파일만 사용해도 된다.

1. Supabase SQL Editor에서 `supabase/migrations/20261015_customer_records.sql`과 `supabase/migrations/20261015_customer_form_options.sql`을 실행한다. 첫 파일은 고객·계약 암호문 저장, 두 번째는 회원별 구분 선택 목록용이다. 이미 적용한 고객·계약 파일을 다시 실행할 필요는 없다. 기존 고객 데이터는 변경하지 않는다.
2. 서버 환경변수 `CUSTOMER_DATA_ENCRYPTION_KEY`를 설정한다. 32바이트 난수의 hex 표현(64자)이며 `NEXT_PUBLIC_` 접두사를 붙이지 않는다. 로컬 `.env.local`에는 생성되어 있다.
3. 배포 서버에도 동일한 키를 별도로 설정한다. 키를 잃으면 암호문을 복구할 수 없으므로 접근 제한된 비밀 저장소에 백업한다. 운영 데이터가 생긴 후 키만 교체하지 않는다. 현재 키 버전은 `v1`이다.

## 동작

- 고객 추가: 이름·생년월일과 수집·이용 확인을 검사하고 계좌 예금주 기본값 및 실손 만기 자동값을 적용한다.
- 고객 기본 생년월일만 7자리(`960901-2`)로 입력한다. 청구 예금주·계약자·피보험자의 생년월일은 6자리이며, 검색과 고객목록에서도 앞 6자리만 표시한다. 계약 연결은 회원별 고객 ID와 이름·앞 6자리 일치를 함께 검사한다.
- 여러 차량은 `vehicles` JSON 문자열로 고객 암호문 안에 저장한다. 각 차량은 차량번호·차종·보험사·갱신일·운전자지정·할인을 가진다. 기존 단일 차량 필드는 첫 차량으로 호환하며, 차량별 데이터는 추가 DB 테이블이나 평문 컬럼에 저장하지 않는다.
- 계약 추가: 로그인 회원의 고객 중 계약자 이름·생년월일이 일치하는 고객에 연결한다. 계약자 자동완성은 해당 회원의 조회 결과를 사용한다.
- 서버에서 AES-256-GCM으로 모든 고객/계약 필드를 암호화한다. 회원 ID·레코드 ID·종류를 AAD에 묶어 암호문을 다른 고객이나 회원으로 옮겨 복호화할 수 없게 한다.
- DB에는 ID·소유 회원 ID·생성/수정 시간 등 메타데이터와 암호문만 저장한다. 이름·연락처·생년월일·계좌·메모와 확인 기록은 암호문 내부에 있다.
- 브라우저의 직접 테이블 접근은 차단한다. 서버가 로그인 토큰과 회원 승인 상태를 확인하고 조회마다 `user_id`로 제한한다.
- 목록은 500건씩 끝까지 조회한다. 브라우저 메모리에서 검색하고, 페이지 새로고침 시 서버에서 다시 읽는다. 로컬스토리지에 고객 데이터를 저장하지 않는다.
- 저장 재시도는 같은 요청 ID를 재사용해 중복 삽입을 막는다. 새 입력/새 팝업은 새 ID를 사용한다.
- 개인정보 확인 체크는 고객 본인의 동의서가 아니라 설계사의 확인 기록이다. 확인 시각·문구 버전을 암호화해서 보관한다.

### 별도 SQL 없이 기존 암호문에 저장하는 항목

- 여러 차량: `vehicles`.
- 체크리스트 및 고객 관리 일정: `checklist`. 관리 항목·예정일·메모·완료 상태를 포함한다.
- 알릴의무: `disclosure`. 질문·답변·상세 내용과 입원 이력(`hospitalizations`)·수술 이력(`surgeries`)을 포함한다. 각각 기본 3행이며 추가 가능하다. 이전 메모는 화면에서 제거하되 기존 저장값은 유지한다.
- 상담일지: `consultations`.
- 상담일지 왼쪽의 상담 관리 표는 같은 `consultations`의 `records` 배열로 저장한다. 상담일·상담 내용·고객 반응·다음 연락일·진행 상태를 검증하며, 오른쪽 상세 메모(`entries`)와 함께 암호화한다. 별도 DB 컬럼이나 SQL 추가는 필요하지 않다.
- 위 항목은 서버에서 검증한 뒤 기존 `encrypted_payload` 안에 저장한다. 차량·의료 이력·일정별 평문 컬럼이나 별도 테이블을 추가하지 않는다.
- 메인페이지 고객 관리 알림은 `/api/customers?view=reminders`에서 로그인 회원의 예정일이 오늘인 미완료 항목을 읽어 표시한다. 별도 알림 테이블을 만들지 않는다. 완료 후 저장하면 제외한다. 생일은 고객 생년월일로 기본 입력하고 다음 생일 날짜로 매년 갱신한다. 직접 수정한 월·일도 유지하며 연도 갱신 시 완료 체크를 초기화한다. 윤년의 2월 29일은 평년에 2월 28일로 표시하되 원래 월·일을 보존한다. 휴대폰 푸시 알림은 구현하지 않았다.
- 메인 캘린더의 일반 일정 알림도 같은 배너에 표시한다. 기본값은 꺼짐(알림 레코드 없음)이며 종 버튼으로 바로 켜고 끈다. 기존 알림 설정/자동 표시 팝업은 사용하지 않는다. 켠 일정은 `calendar_reminders`에 저장하며 오늘인 일정만 배너에 포함한다. 끄면 레코드를 삭제해 배너에서 제외한다. 기존 고객 일정 알림과 별도 opt-in이며, 기존 알림 SQL이 통합 파일에 포함되어 있으므로 이 UI 변경에 따른 추가 SQL은 없다.
- 캘린더 고객 일정은 `/api/customers?view=calendar&from=...&to=...`에서 본인 고객의 생일·차량별 갱신·계약 면책/감액 만료를 반환한다. 기존 스프레드시트 일정과 함께 표시하며 고객정보 원문은 캘린더 전용 응답에 포함하지 않는다. 완료 상태는 고객정보와 별개로 `customer_settings.calendar_completed`에 저장한다. 면책/감액은 기존 시트와 같은 계약일+입력 개월 수 기준으로 계산하며, 정확한 약관별 만료 경계 확정은 남아 있다.

위 적용 상태는 준비 완료와 실제 DB 실행 확인을 구분한다. 자동 테스트는 메모리 DB를 사용하므로 운영 DB 적용 증거로 취급하지 않는다.

고객 및 계약의 추가·조회·수정·삭제를 연결했다. 계약현황의 메모 오른쪽 수정·삭제 아이콘으로 조작하며, 수정은 기존 계약을 채운 팝업을 열고 삭제는 확인을 거친다. 계약 삭제는 해당 계약만 제거한다. 고객 삭제 시 연결 계약도 함께 삭제되며, 화면에서 확인 팝업을 먼저 표시한다. 수정·삭제는 소유권과 revision 검사로 다른 회원의 데이터나 다른 창에서 변경한 내용을 덮어쓰지 않는다. 계약 수정·삭제를 위한 추가 SQL은 필요하지 않다.

목록 기본 순서는 최근 등록순이다. 고객 카드 자체를 드래그해 순서를 바꾸며 회원별로 DB에 저장한다. `supabase/migrations/20261015_customer_record_order.sql`을 추가 적용해야 한다. 실패 시 화면 순서를 되돌린다. 검색 중에는 보이는 고객끼리만 순서를 바꾸고 숨겨진 고객 위치는 유지한다. 신규 고객은 저장한 순서 위에 표시된다.

동의서 증빙, 보관기간 만료에 따른 파기와 백업 삭제 정책은 아직 구현하지 않았다. 계약 면책/감액 만료일의 날짜 경계 기준은 별도로 확정해야 한다.

알릴의무는 고객 암호문 내부의 `disclosure` JSON 문자열로 저장한다. 4개 질문의 문구·예/아니오·상세 내용을 수정하고 저장할 수 있다. 추가 DB 테이블은 사용하지 않는다. 마지막 상세 탭 ID만 `customer-detail-tab:<회원 ID>` 로컬스토리지에 저장하며, 질문·답변·상세 내용은 로컬스토리지에 쓰지 않는다.

상담일지는 같은 고객 암호문의 `consultations` JSON 문자열에 등록·수정·삭제한다. 날짜는 커스텀 달력에서 선택하고 시간(HH:mm), 장소, 상담 내용을 입력한다. 목록은 상담 날짜·시간의 최신순으로 표시한다. 삭제 시 확인 팝업을 거치며, 고객 revision 검사로 다른 창의 변경 내용을 덮어쓰지 않는다. 상담 내용도 로컬스토리지에는 저장하지 않는다.

검증: `node --test lib/customer-records.test.mjs app/my-page/customer-lookup-model.test.mjs` 및 `npx tsc --noEmit`.
테스트는 가짜 데이터와 메모리 DB를 사용하며 실제 고객정보를 넣지 않는다.

고객 알림 배너에서 날짜는 표시하지 않는다. 알림 클릭으로 확인 팝업을 열고 완료 체크하면 서버 `complete-schedule` 작업으로 고객 암호문의 같은 일정 항목을 완료 처리한다. 소유권·해당 날짜·revision을 검사하며, 완료 항목은 배너에서 제외하고 고객관리 목록을 갱신한다. 별도 SQL은 필요하지 않다.
